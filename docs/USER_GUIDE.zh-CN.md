# agent-tracker 用户使用手册

## 1. 当前版本能做什么

截至当前仓库实现，`agent-tracker` 已经进入最小 Ink 交互界面可用阶段。

现在已经具备的内容：

- Bun 项目已经初始化完成
- TypeScript 基础配置已经存在
- 有一个 Ink 界面入口 `src/bin.ts`
- 已实现“统计 / 提交 / 仪表盘 / 设置 / 健康”五类固定主视图
- 已实现“信息区 / 详情区 / 水平导航 / 快捷键”的上下布局
- 已实现内部路由概念，已支持统计、提交、文件详情和健康页下钻
- 已实现已完成一次性动作的自动降级
- 已实现“初始化仓库”动作
- 已实现“执行健康检查”动作
- 已实现“安装 Cursor 集成”动作
- 已实现最小的 Cursor hook 事件写入能力
- 已实现 branch / commit / file 的行级 AI 统计
- 已实现提交列表、提交详情、文件详情三级下钻
- 已实现本地浏览器 dashboard
- 已实现 `Human` 证据链：人工快照、reconcile 快照、改写已知 AI 行

现在还没有实现的内容：

- 团队共享或远程 dashboard

这意味着，当前版本已经可以统计分支、commit、文件三级的 AI / Human / Unknown 数据，并完成基础接入动作：

- 通过终端界面初始化当前 Git 仓库的 `agent-tracker` 配置
- 通过终端界面检查当前仓库是否处于可继续接入采集和统计的状态
- 为当前仓库安装 Cursor hooks
- 把最小的 Cursor hook 事件写入本地 raw trace 文件

## 2. 环境准备

使用当前仓库前，需要先准备：

- Bun 1.3+
- Git

如果只是运行当前项目，Cursor 还不是必需项；只有在后续接入 hooks 采集时，才会成为必需依赖。

## 3. 当前版本的使用方式

### 3.1 安装依赖

在项目根目录执行：

```bash
bun install
```

### 3.2 启动交互界面

执行：

```bash
bun run dev
```

如果你已经执行过构建，也可以直接运行发布产物：

```bash
bun ./dist/index.js
```

启动后，当前界面提供：

- 默认统计视图：优先展示当前分支和 commit 范围内的摘要
- 水平一级导航：`统计 / 提交 / 仪表盘 / 设置 / 健康`
- 上方信息区：展示当前状态、分支范围和最近结果
- 中间详情区：展示统计、提交详情、文件 diff 或健康数据
- 底部快捷键区：固定展示当前可用键位
- 来源分支直接读取当前分支，不需要配置 `source_branch`
- 已完成的一次性动作会自动降级，比如初始化和安装集成

### 3.3 当前界面的基本操作

当前可用快捷键：

- `← / →` 在统计、提交、仪表盘、设置、健康之间切换
- `↑ / ↓` 在提交、文件或任务列表中移动选择，或在文件 diff 中滚动
- `[` / `]` 在文件详情里切换上一文件 / 下一文件
- `Enter` 打开当前选中的提交、文件或执行当前任务
- `Esc / Backspace` 返回上一层
- `r` 刷新当前统计
- `Ctrl+C` 退出界面

如果需要浏览器端 dashboard，可以直接执行：

```bash
bun run dashboard
```

### 3.4 初始化当前仓库

如果当前仓库还没有初始化，请先切到“设置”页，再按 `Enter` 执行“初始化当前仓库”。

这一步会完成：

- 检查当前目录是否是 Git 仓库
- 创建 `.agent-tracker/config.toml`
- 创建本地状态目录 `.git/agent-tracker/`
- 提示当前是否已安装 Cursor hooks

### 3.5 执行健康检查

当仓库存在风险提示时，请切到“健康”页，再按 `Enter` 执行完整健康检查。

当前它会检查：

- Git 仓库是否存在
- 当前分支、目标分支是否可解析
- 是否可以做 fast-forward compare
- 项目配置文件是否存在
- 本地状态目录是否存在
- Cursor hooks 是否已安装
- 当前是否已经采集到 raw trace 数据

### 3.6 安装 Cursor Hook 集成

如果项目配置已经存在但 Cursor 集成尚未安装，请切到“设置”页，再按 `Enter` 执行“安装 Cursor 集成”。

这一步现在已经实现，当前会完成：

- 在仓库内创建或更新 `.cursor/hooks.json`
- 创建 `.cursor/hooks/agent-tracker-hook.sh`
- 为 `afterFileEdit`、`afterTabFileEdit`、`afterShellExecution`、`sessionStart`、`sessionEnd` 安装采集入口
- 不把本地 raw trace 放进 Git，而是写到 `.git/agent-tracker/raw/`

### 3.7 当前版本的真实采集和统计能力

如果 Cursor hooks 被触发，当前版本已经可以把 hook payload 以最小 raw trace 形式写入：

- `.git/agent-tracker/raw/YYYY-MM-DD.jsonl`

当前已经可以做到：

- branch 级 AI 行统计
- commit 级 AI 行统计
- 基于“人工快照 / reconcile 快照 / 改写已知 AI 行”的 Human 行统计
- 文件级 diff 展示
- 在 dashboard 里浏览 branch / commit / file 数据

### 3.8 当前版本的能力边界

虽然终端和 dashboard 都已经能看统计，但下面这些仍然没有实现：

- 更细粒度的人工保存来源区分
- 更复杂历史操作下的高精度追踪
- 团队共享或远程看板

## 4. 站在用户视角，未来应该怎样使用

虽然当前实现还没有完整能力，但从产品体验角度，推荐未来把用户流程整理成下面这条主路径：

### 4.1 初始化项目

用户进入一个 Git 仓库后，执行：

```bash
agent-tracker
```

然后在“设置”页执行初始化动作。

这条路径现在已经初步实现，当前能完成：

- 检查当前目录是否是 Git 仓库
- 创建本地状态目录
- 生成默认配置
- 检查 Cursor hooks 是否已安装
- 在右侧给出下一步操作提示

### 4.2 检查环境

用户进入界面后，如果仓库存在风险提示，先切到“健康”页，再执行完整健康检查。

这一步现在已经初步实现，当前会告诉用户：

- 当前来源分支和目标分支是什么
- Git 是否已同步到可比较状态
- 是否能 fast-forward compare
- Cursor hooks 是否工作正常
- 本地是否已经采集到 trace 数据

### 4.3 开始采集

未来理想状态下，用户在 Cursor 里正常写代码，不需要额外学习新的工作流。

理想状态下，工具自动完成：

- 捕获文件编辑事件
- 记录 AI 生成相关元数据
- 将 trace 写入本地存储

### 4.4 查看分支统计

未来用户进入界面后，默认就会落在分支统计视图，而不是再去记命令。

它应该展示：

- 当前分支总 AI 占比
- commit 数量
- 自己和他人的 commit 分布
- unknown 占比
- 是否存在数据缺口

### 4.5 查看单个 commit 详情

未来用户只需要在“最近提交”视图里继续下钻，不需要额外记命令。

它应该展示：

- 当前 commit 的 AI 比例
- 涉及的文件
- 哪些文件区块来自 AI
- 关联的会话或 trace 信息

### 4.6 交互式使用

未来用户直接执行：

```bash
agent-tracker
```

进入交互模式后，用户直接通过水平导航选择页面即可，比如：

- 统计
- 提交
- 仪表盘
- 设置
- 健康

## 5. 当前流程中值得优化的方向

基于当前仓库状态和未来目标，从用户视角看，最值得优先优化的是下面几件事。

### 5.1 把“从零开始”路径压缩到最短

理想情况是用户只需要三步：

1. `bun install`
2. `agent-tracker`
3. 在 Cursor 中继续正常工作

现在虽然已经有 Ink 界面、初始化、健康检查和 Cursor 安装动作，但离真正的“开箱即用”还有距离。后续实现时，应该继续避免让用户手动复制 hooks 文件、手动改配置、手动创建目录。

### 5.2 优先做好“健康检查”

从真实使用角度看，用户最容易困惑的不是“怎么查看统计”，而是“为什么没有数据”。

所以“健康检查”的优先级应该非常高。它最好一屏就解释清楚：

- 为什么当前没有采集数据
- 是 hooks 没装，还是 Git 不同步
- 是 branch 配错，还是 Cursor 没触发编辑事件

### 5.3 优先做“默认可用”的配置

大多数用户不希望第一天就写配置文件。

推荐默认值：

- `target_branch = main`
- 存储目录默认放在 `.git/agent-tracker/`

这样用户第一次使用时，只需要在特殊情况下修改 `target_branch` 等少量配置。

### 5.4 把“错误提示”设计成下一步指令

不要只报错：

- `branch not synced`
- `no traces found`

更好的方式是直接告诉用户下一步做什么，比如：

- `Run git fetch origin first`
- `进入“设置”页并执行“安装 Cursor 集成”`
- `等后续实现后再执行 reconcile`

### 5.5 先保证 TUI 主路径清晰，再做更复杂的展示

从用户价值上看：

- 清楚、可信的统计结果
- 稳定的排障信息
- 可复现的命令输出

这些比复杂终端 UI 更重要。

所以产品实现顺序上，建议先把：

- 概览 / 设置 / 健康
- Cursor hooks 安装
- branch
- show

做扎实，再继续扩展 `/` 命令面板和 dashboard。

### 5.6 明确区分“没有采集到”和“人工编写”

这是用户信任感的关键。

如果系统没有采到 trace，不应该默认算成人工代码。更合理的是保留 `unknown`，并明确提示数据可能不完整。否则用户会很快失去对统计结果的信任。

### 5.7 第一版就加“清理数据”能力

只要涉及本地状态存储，用户就会关心两件事：

- 数据存在哪
- 能不能删

所以后续版本里，`clear` 和 `export` 不应该拖得太后。

## 6. 推荐的近期落地顺序

如果从“用户最快能真正用起来”的角度排优先级，推荐顺序是：

1. 继续打磨 `init`
2. 继续打磨“健康检查”
3. 继续完善 Cursor hooks 安装与采集
4. 把 raw trace 演进成可归因的数据模型
5. `branch`
6. `show <commit>`
7. `/` 交互命令面板
8. dashboard

## 7. 当前版本的结论

如果你现在是第一次进入这个仓库，可以把它理解为：

- 底层运行环境已经搭好
- 项目方向和产品方案已经比较清晰
- Ink 主界面、初始化、健康检查和 Cursor 安装动作已经开始落地
- 最小 raw trace 采集链路已经接通
- 但归因计算和展示层还没有开始实现

所以当前最适合的使用方式，不是“作为成品统计工具来使用”，而是“作为一个已经具备最小 Ink 交互骨架、可以继续往采集和分析功能推进的项目来继续开发”。
